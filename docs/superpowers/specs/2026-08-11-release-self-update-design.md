# Release self-update design

Status: Implemented on `release-self-update`, pending final exact-head verification

## Goal

Allow a user to update an installed `github-delivery` skill directly from the installed skill directory without cloning the repository or manually downloading a new bundle.

The public interface is:

```text
node scripts/install-skill.mjs --update
node scripts/install-skill.mjs --update --apply
```

`--update` is read-only with respect to the installed target and produces a verified plan. `--update --apply` executes only that already-validated update path.

The updater installs only published, non-draft, non-prerelease GitHub Releases from `Wibias/github-delivery`. It never installs `main`, a branch, a source archive generated by GitHub, or an unpublished build.

## Non-goals

- Automatic background updates.
- Updating from `main`, arbitrary refs, forks, or user-supplied URLs.
- Replacing the existing install/backup/restore implementation.
- Bypassing Codex hook trust after an update.
- Implementing Sigstore verification directly in Node.
- Supporting prerelease channels in v1.
- Downgrading through `--update`.

## User experience

### Check only

From an installed skill directory:

```text
node scripts/install-skill.mjs --update
```

The command performs release discovery, downloads the required release metadata/assets into a temporary directory, validates the candidate, and prints a machine-readable plan without replacing the installed skill.

The stable update planner uses these action values:

- `update`: a strictly newer verified release is available and the installed tracked payload is clean;
- `already_current`: the installed version equals the latest published stable release;
- `already_ahead`: the installed version is newer than the latest published stable release;
- `blocked_local_modifications`: a strictly newer verified release exists, but tracked installed files differ from the installed manifest and replacement is forbidden.

Current/ahead states remain no-ops even when local drift exists. The drift is still reported and `safeToReplace` remains false, but no replacement is attempted because there is no newer release to install.

This distinction matters during release preparation, when a locally installed bundle can be ahead of the latest published GitHub Release. `--update` never interprets that as permission to downgrade.

### Apply

```text
node scripts/install-skill.mjs --update --apply
```

If and only if the release candidate is newer, fully verified, and the installed payload is safe to replace, the updater reuses the existing installation machinery for backup and atomic replacement.

The successful result reports the previous version, installed version, backup path, release tag, verified release source commit, and resulting watchdog activation state.

The legacy `scripts/update-skill.mjs` entrypoint is only a compatibility wrapper. It prepends `--update` and forwards all caller arguments to the normal installer, so there is one acquisition/verification path and one mutation path.

## Release discovery

The updater calls the GitHub Releases API endpoint for the latest published release of the fixed upstream repository:

```text
https://api.github.com/repos/Wibias/github-delivery/releases/latest
```

The repository identity is a constant in the updater. v1 does not accept a repository override.

The release must satisfy all of the following before any installation planning continues:

- `draft` is false;
- `prerelease` is false;
- `tag_name` exactly matches `vX.Y.Z`;
- the version extracted from the tag is valid strict semantic `X.Y.Z`;
- the required release assets exist exactly once;
- asset names match the tag version;
- duplicate names or ambiguous release assets fail closed.

Required assets:

```text
github-delivery-vX.Y.Z.zip
manifest.json
SHA256SUMS
```

The `.tar.gz` and SBOM may remain published release assets, but the v1 self-updater uses the ZIP bundle on every platform so extraction and security validation have one implementation and one test corpus.

## Trust and verification chain

The updater does not trust a release merely because it came from a GitHub Release page. It requires all verification layers below.

### 1. GitHub release asset digest

For every downloaded required asset for which GitHub exposes a `sha256:` asset digest, the downloaded bytes must match that digest.

A malformed digest or a mismatch fails closed.

### 2. `SHA256SUMS`

`SHA256SUMS` is parsed strictly. The ZIP and `manifest.json` must each have exactly one valid SHA-256 entry, and the downloaded bytes must match those entries.

Malformed lines, duplicate entries for required assets, unsupported hash formats, missing entries, or mismatches fail closed.

### 3. Manifest identity

The downloaded `manifest.json` must satisfy the distribution contract:

- `schemaVersion === 1`;
- `kind === "github-delivery/distribution-manifest"`;
- `name === "github-delivery"`;
- `version` equals the release tag version;
- `sourceCommit` is a 40-character hexadecimal commit SHA;
- `files` is a finite list of unique relative payload paths;
- every entry has the expected SHA-256/size/mode shape;
- paths are normalized and cannot escape the `github-delivery` root.

### 4. Tag/source-commit binding

The updater resolves the exact tag through the GitHub API and requires the tag's peeled commit SHA to equal `manifest.sourceCommit`.

Annotated and lightweight tags are both supported, but the final peeled object must be a commit. Tag peeling is bounded and cycle checked.

This ensures the manifest identifies the exact commit selected by the published release tag.

### 5. GitHub artifact attestation

The ZIP must pass GitHub artifact-attestation verification using the installed GitHub CLI.

The updater invokes `gh attestation verify` with constraints that bind the artifact to:

- repository `Wibias/github-delivery`;
- signer workflow `Wibias/github-delivery/.github/workflows/release.yml`;
- source ref `refs/tags/vX.Y.Z`;
- source digest equal to the resolved release-tag commit.

The attestation command must exit successfully. Missing `gh`, missing verification support, a failed attestation, a signer mismatch, source-ref mismatch, or source-digest mismatch fails closed.

There is no checksum-only fallback in v1.

The updater may use unauthenticated GitHub API/download requests for public release reads. If GitHub rate limits or transport failures prevent release validation, the command fails without modifying the installed skill.

## Download behavior

Network access is implemented behind a small injected release-client interface so tests do not require live GitHub access.

Production behavior:

1. Fetch latest release metadata.
2. Validate release metadata before downloading payloads.
3. Download only the required assets into a newly created private temporary workspace.
4. Enforce bounded response sizes appropriate to the current release format.
5. Follow redirects manually, allow only HTTPS destinations, and bound redirect count.
6. Reject unexpected content that exceeds configured limits before writing unbounded data.
7. Clean the temporary directory on success and every failure path.

The updater never stores bearer tokens, arbitrary API response bodies, or downloaded artifacts in the installed skill directory.

## Archive extraction security

The ZIP is treated as hostile even after transport/integrity verification and is extracted with a strict format reader.

Extraction rejects:

- absolute paths;
- drive-letter, UNC, or backslash paths;
- `..` path traversal;
- empty or malformed names;
- NUL-containing names;
- entries outside the single `github-delivery/` root;
- duplicate normalized paths;
- symbolic links or other link-like entries;
- unsupported special-file modes;
- unsupported compression methods;
- files absent from the manifest;
- a manifest-declared file missing from the archive;
- archive `manifest.json` bytes that differ from the separately downloaded verified `manifest.json`;
- CRC failures;
- unsafe destination path components;
- per-file, entry-count, or total expansion limits.

Directories may be implicit. Regular files are written only beneath a private extraction root.

After extraction, every manifest file is rehashed and its exact byte count is checked. No call into the installation layer occurs until the extracted payload completely matches the verified manifest.

## Version semantics

Version comparison uses strict numeric `major.minor.patch` values only, matching the repository's release contract.

Given installed version `I` and latest verified release version `R`:

- `R > I` and the installed tracked payload is clean: `update`;
- `R > I` and the installed tracked payload has drift: `blocked_local_modifications`;
- `R === I`: `already_current`;
- `R < I`: `already_ahead`.

Local drift is always measured and reported. For `already_current` and `already_ahead`, drift sets `safeToReplace` false but does not change the no-op action because there is no replacement to authorize. For a strictly newer release, local drift blocks replacement.

`--allow-downgrade` does not change `--update` behavior and is rejected in update mode. The existing explicit local-source downgrade mechanism remains separate. `--force` cannot bypass the self-update local-modification guard for a newer replacement.

## Integration with the existing installer

Self-update is an acquisition and verification layer in front of the existing distribution installer, not a second installer.

High-level modules:

```text
scripts/lib/release-self-update.mjs
scripts/lib/release-zip.mjs
scripts/lib/stable-release-update.mjs
```

Responsibilities include:

- latest-release discovery;
- release/tag/asset validation;
- bounded downloads and redirect validation;
- SHA-256 verification;
- manifest validation;
- tag/source-commit verification;
- attestation invocation through an injectable runner;
- safe ZIP extraction;
- installed-manifest drift/version planning;
- producing a verified temporary source directory and update metadata.

Existing `scripts/install-skill.mjs` remains the CLI entrypoint and owns `--update` parsing and application.

The flow is:

```text
parse args
  -> acquire + verify release candidate
  -> verify exact tag/source commit + attestation
  -> strict extract + rehash candidate
  -> compare installed/latest versions and installed manifest
  -> if current/ahead: return no-op result with drift diagnostics
  -> if newer + local modifications: fail closed
  -> if dry-run: return verified plan
  -> if --apply: existing installSkill()/applyInstallation() path
  -> existing Codex hook/watchdog handling
  -> post-install manifest + config verification
  -> cleanup
```

The updater supplies the extracted `github-delivery` directory as `source` to the existing installer only after the candidate has been fully verified. Existing target, backup-root, Codex-home, host detection, hook trust, watchdog, backup, and restore behavior remains authoritative.

`--update` and `--restore` are mutually exclusive. Supplying `--source` together with `--update` is rejected so an apparent release update cannot silently use an arbitrary local source. `--allow-downgrade` is also rejected in update mode.

Unless `--target` is explicitly supplied, update mode targets the root of the installed bundle that is running `install-skill.mjs`, rather than the install command's normal default target.

## Hook and watchdog semantics after update

A self-update reuses the existing Codex hook installation path after the new skill payload has been installed.

A previously trusted hook definition is not automatically trusted if the exact configured definition changes during the update.

Therefore:

- unchanged expected hook definition plus an explicitly supplied valid `--hook-trust-verified` assertion may remain verified under the existing rules;
- changed hook definition causes `hook_trust_required`;
- the updater never adds `--dangerously-bypass-hook-trust`;
- stream capability is not claimed unless the existing controlled-launch conditions are actually met.

## User configuration

Persistent user configuration is outside the installed skill payload and is not part of the release replacement source.

For an applied update, the updater snapshots the effective user config before replacement and rereads it after post-install payload verification. Any unexpected change fails closed with `stable_update_user_config_changed_unexpectedly`.

The update workflow must not silently adopt new settings merely because a new release supports them. New configuration options are reviewed after a successful update and changed only with explicit user intent.

## Post-install verification

After the existing installer reports a completed replacement, the updater reopens the installed target and verifies:

- installed `manifest.json` is structurally equal to the separately verified release manifest;
- every manifest file exists and matches its expected hash and byte count;
- the existing installer has completed its normal hook/watchdog activation behavior;
- persistent user configuration is unchanged.

If the replacement itself succeeded but post-install payload or config verification fails, the command throws a failed postcondition and attaches the created backup path for operator recovery. It does not silently claim success.

The existing restore command remains the recovery mechanism.

## Error behavior

Before replacement, every error is non-mutating with respect to the installed skill.

Representative error classes:

- latest release unavailable;
- latest release malformed/draft/prerelease;
- required asset missing/duplicated;
- invalid/non-HTTPS redirect or redirect limit;
- download failure/size limit;
- GitHub asset digest mismatch;
- malformed or mismatching `SHA256SUMS`;
- malformed manifest;
- version/tag/asset mismatch;
- tag does not resolve to manifest source commit;
- `gh` unavailable;
- attestation verification failure;
- unsafe ZIP entry;
- ZIP/manifest mismatch;
- local installed modifications that block a newer replacement;
- existing installer preflight failure;
- replacement/postcondition failure;
- unexpected persistent user-config change.

Errors contain actionable class/reason text without dumping release payloads, tokens, or arbitrary response bodies. If an error occurs after replacement and the installer created a backup, the CLI also reports that backup path.

## Testing strategy

Tests remain deterministic and offline.

### Release-client tests

Use an injected fake client to cover:

- valid newer release;
- same version;
- installed version ahead of latest release;
- draft/prerelease rejection;
- invalid tag/version;
- missing/duplicate assets;
- asset digest mismatch;
- transport failure;
- redirect safety;
- bounded-download enforcement.

### Checksum/manifest/tag tests

Cover:

- valid `SHA256SUMS`;
- missing/duplicate/malformed entries;
- manifest name/version/source-commit mismatch;
- duplicate/unsafe manifest paths;
- lightweight tag resolution;
- annotated tag peeling;
- cycle/depth rejection;
- tag/source-commit mismatch.

### Attestation tests

Use an injected command runner:

- assert the exact repository, signer-workflow, source-ref, and source-digest constraints;
- success permits the flow to continue;
- missing `gh` fails closed;
- non-zero verifier exit fails closed;
- no checksum-only fallback.

### Archive-security tests

Use crafted local ZIP fixtures for:

- normal payload;
- `../` traversal;
- absolute path;
- Windows drive/UNC/backslash path;
- duplicate normalized entry;
- symlink mode;
- unsupported compression/type;
- extra undeclared file;
- missing manifest-declared file;
- archive manifest mismatch;
- CRC mismatch;
- unsafe destination path;
- file/entry/total expansion limits.

### Installer integration tests

Cover:

- dry-run performs no target mutation;
- `--update --apply` upgrades through existing backup/atomic replacement;
- same-version and already-ahead are no-op even with `--apply`, including when drift diagnostics are present;
- `--update` rejects `--source`, `--restore`, and `--allow-downgrade` combinations;
- local modifications block a newer replacement even when the caller supplied `--force`;
- failed candidate verification never reaches installation;
- hook definition changes invalidate trusted activation under the existing installer rules;
- successful update verifies the final installed manifest and user config;
- backup path is surfaced if post-install verification or config preservation fails;
- the legacy updater delegates to the same installer update path.

## Acceptance criteria

The feature is complete when all of the following are true:

1. An installed skill can check for the latest published release without a repository checkout.
2. Dry-run is the default and performs no installed-skill replacement.
3. `--update --apply` installs only a strictly newer verified release.
4. Same-version and already-ahead states are safe no-ops, including when local drift is reported diagnostically.
5. Drafts, prereleases, branches, `main`, arbitrary URLs, and downgrades are not installable through `--update`.
6. The ZIP must pass GitHub asset digest checks where exposed, `SHA256SUMS`, manifest validation, tag/source-commit binding, and constrained GitHub artifact-attestation verification including source digest.
7. Missing or failed attestation verification has no weaker fallback.
8. Unsafe ZIP structures and manifest mismatches are rejected before installation.
9. Existing backup, atomic replacement, hook trust, watchdog activation, and restore semantics remain authoritative.
10. Local installed modifications cannot be bypassed with `--force` when a newer release would otherwise replace the installation.
11. Successful replacement is followed by installed-manifest verification and user-config preservation checks; failed postconditions surface the backup path.
12. Tests are offline/deterministic and cover the verification chain plus archive attack classes.
13. README, INSTALL, update workflow, and changelog describe the self-update path accurately.
14. Repository CI, architecture contracts, dependency review, and CodeQL are green on the final PR head.
